# X capture, the Instagram way

*Research report, 5 September 2026. Technical scope only.*

How to add an X (formerly Twitter) mode to SWM that drives a signed-in
Chrome window on a dedicated account, reads what X serves its own web
client, and writes the same evidence package the Instagram mode does:
WARC, normalised records, full-size media with fixity, and provenance
back to the saved response.

| Sources read | Claims extracted | Verified 3 of 3 | Approach |
| --- | --- | --- | --- |
| 20 | 97 | 13 (the rest unverified; none refuted) | Observe the page's own requests |

**How to read the badges.** *Verified* means three independent checks
agreed and none refuted the claim. *Unverified* means the claim was
extracted from a source but the check did not run: the research harness
ran out of session budget after thirteen claims and before synthesis, so
this report was written from the extracted claims by hand. Where several
independent sources agree, the text says so.

## Verdict

Build it exactly like the Instagram mode, and it is easier there.

Every open-source X reader that builds its own requests spends its life
chasing three moving parts: the GraphQL operation ids rotate, the
forty-odd `features` flags drift, and the `x-client-transaction-id`
header is generated by an obfuscated script that is re-deobfuscated daily
by the people who track it. SWM's design sidesteps all three. The browser
makes the requests; SWM only has to recognise them and read the answers.
Three things make X simpler than Instagram for that design:

- **The operation name is in the URL.** Every call is
  `GET https://x.com/i/api/graphql/<queryId>/<OperationName>`, so a
  request is recognised from its path alone, with no form body to parse.
  *(verified)*
- **Timelines are typed.** A response is a list of instructions
  (`TimelineAddEntries`, `TimelinePinEntry`, cursors) whose entries carry
  an `entryId` prefix that says what they are: a tweet, a thread module,
  a "who to follow" module, a cursor. Injected modules are separable by
  name, not by guesswork. *(verified)*
- **The account has a stable numeric id.** `UserByScreenName` returns
  `rest_id`; every tweet carries its author's `rest_id`. Attribution is
  an integer comparison, the rule the Instagram mode arrived at after the
  contamination bug. *(verified)*

> **What needs a decision.** Reposts: keep them as the account's own
> entries (they are, on the account's timeline) with the original tweet
> attached, or skip them. Replies tab: the thread modules mix in other
> people's tweets as context; this report proposes keeping only the
> account's own tweets as records and the rest as context, as the
> Instagram mode does with foreign posts.

## What the signed-in client asks for

These are the operations a profile visit, a post page and a search make.
SWM observes them from the page; the ids in the path change and must
never be hard-coded. *(verified)*

| Operation | When the page sends it | Key variables | Where the data is |
| --- | --- | --- | --- |
| `UserByScreenName` | Opening a profile | `screen_name` | `data.user.result`: `rest_id`, `legacy.screen_name`, `legacy.pinned_tweet_ids_str` |
| `UserTweets` | Posts tab, first page and every scroll | `userId` (the rest_id), `count`, `cursor`, `includePromotedContent` | `data.user.result.timeline.timeline.instructions[]` |
| `UserTweetsAndReplies` | Replies tab | as above | same; entries are mostly `profile-conversation-` modules |
| `UserMedia` | Media tab (signed-in only) | as above, `includePromotedContent: false` | same |
| `TweetDetail` | A post page, and "show more replies" | `focalTweetId`, `cursor`, `with_rux_injections`, `withCommunity` | `data.threaded_conversation_with_injections_v2.instructions[]` |
| `SearchTimeline` | Search and hashtag pages | `rawQuery`, `product` (Top, Latest, Media), `cursor` | `data.search_by_raw_query.search_timeline.timeline.instructions[]` |
| `TweetResultByRestId` | Used by yt-dlp for a single post; the web client uses TweetDetail | `tweetId` | `data.tweetResult.result` |

Each request carries three JSON query parameters: `variables`,
`features` and, for some operations, `fieldToggles`. The headers a
signed-in call needs are the public web bearer token, `x-csrf-token`
copied from the `ct0` cookie, `x-twitter-auth-type: OAuth2Session`,
`x-twitter-active-user: yes`, an `x-client-transaction-id`, and the
HttpOnly `auth_token` cookie. *(verified)* SWM never has to produce any of
these; the response hook sees them, and the request-side redaction must
strip `x-csrf-token`, the bearer and the cookies from the WARC as it does
for Meta's.

TweetDetail's response path above is from the open-source readers' code
rather than the OpenAPI spec and is marked unverified in the evidence
table; confirm it against the first capture.

## Timeline anatomy

A timeline response is a list of typed instructions. *(verified)* The
shape SWM's extractor should walk, with the paths that hold what it needs:

```text
data.user.result.timeline.timeline.instructions[]
  TimelinePinEntry        .entry            the pinned post; cross-check legacy.pinned_tweet_ids_str
  TimelineClearCache
  TimelineAddEntries      .entries[]
    entryId  "tweet-<id>"                      one post
             "profile-conversation-<id>"      a thread module: content.items[].item.itemContent
             "who-to-follow-…" "module-…"     injected: skip
             "messageprompt-…"                injected: skip
             "cursor-top-…" "cursor-bottom-…" content.value, content.cursorType
    content.__typename  TimelineTimelineItem | TimelineTimelineModule | TimelineTimelineCursor
    content.itemContent.tweet_results.result
      __typename  Tweet | TweetWithVisibilityResults (.tweet) | TweetTombstone | TweetUnavailable
      rest_id
      core.user_results.result   rest_id, legacy.screen_name        the author
      legacy                     full_text, created_at, conversation_id_str,
                                 in_reply_to_status_id_str, entities, extended_entities.media[]
      note_tweet.note_tweet_results.result.text   the full text of a long post
      legacy.retweeted_status_result.result       a repost: the original post inside
      quoted_status_result.result                 a quote: the quoted post inside
  TimelineAddToModule     .moduleItems[]     more items for an existing module
  TimelineReplaceEntry    .entry_id_to_replace, .entry
  TimelineTerminateTimeline  .direction Top | Bottom | TopAndBottom
```

- Unwrap by `__typename`: `TweetWithVisibilityResults` wraps the real
  tweet under `tweet`; `TweetTombstone` and `TweetUnavailable` (reasons
  such as `NsfwLoggedOut`, `Protected`) are records of absence and belong
  in the events, not the posts. *(verified)*
- Long posts: the text is in `note_tweet.note_tweet_results.result.text`;
  `legacy.full_text` is the truncated form. Merge URL entities from both.
  *(verified)*
- Media lives in `extended_entities.media`, not `entities.media`, typed
  `photo`, `video`, `animated_gif`. *(verified)*
- Reposts and quotes: try the legacy id fields first, then
  `retweeted_status_result.result.rest_id` and
  `quoted_status_result.result.rest_id`; a result whose `__typename` is
  `UserUnavailable` has no author. *(verified)*
- Cursors carry `cursorType` (Top, Bottom, ShowMore, ShowMoreThreads,
  Gap), a `value` string, and `stopOnEmptyResponse`. *(verified)* Cursor
  values are Base64 Thrift structs, not opaque, but SWM has no reason to
  decode them. *(unverified)*

## Whose post is it

The rule that fixed the Instagram contamination applies unchanged: a
record is the account's when the account's own listing request returned
it and the post names no other owner, with the numeric id deciding.

1. **Resolve the account first.** Read `rest_id` from the
   `UserByScreenName` response the page makes on opening the profile.
   Every later check is against that number. *(verified)*
2. **Accept only listing operations.** A post counts only when read from
   a `UserTweets`, `UserTweetsAndReplies` or `UserMedia` response whose
   `variables.userId` equals the account's rest_id. The signed-in page
   also makes home-feed and notification calls that carry other people's
   posts; they are recorded but never listed.
3. **Drop injected entries by name.** Skip entries whose `entryId` starts
   with `who-to-follow-`, `module-`, `messageprompt-` or `cursor-`.
   *(unverified)* Promoted posts: twscrape and gallery-dl request
   `includePromotedContent` and filter afterwards; Browsertrix recognises
   them in the page by a `placementTracking` element. Look for a
   `promotedMetadata` object on the item in the first captures and add it
   to the skip rule.
4. **Compare the author.** `core.user_results.result.rest_id` must equal
   the account's rest_id. A repost passes this test (the account made it)
   and carries the original under `retweeted_status_result`; a reply in a
   thread module passes only for the account's own tweets, and the
   neighbours in the module are context.
5. **Pinned posts.** Take them from the `TimelinePinEntry` instruction and
   confirm against `legacy.pinned_tweet_ids_str` on the user; they sit
   first regardless of date, exactly like Instagram's, so the latest-N and
   date-range rules that already treat pinned posts separately carry
   over. *(verified)*

## Pagination and knowing when a timeline ends

The page pages by sending the value of the entry whose `cursorType` is
`Bottom` back as `variables.cursor`. In SWM's design the browser does
that when scrolled; SWM only has to notice the new response and its
cursor. *(unverified; three sources agree)*

The end is not signalled by a missing cursor. X keeps returning a bottom
cursor on an exhausted timeline, so the readers use three different stop
rules: no new tweet ids for three consecutive pages (twitter-api-client);
the cursor equal to the one just sent or absent, with a tolerance for
pages that hold only a cursor (gallery-dl); a repeated cursor or three
empty pages (twscrape). *(unverified)* SWM's stall-round rule from
Instagram, "no post not yet seen after N scrolls", is the same idea and
needs no change. Two ceilings to record in the manifest: X returns roughly
3,200 tweets at most through UserTweets and UserTweetsAndReplies, and a
page holds 20 to 40 entries depending on the client's `count`.
*(unverified)*

For **since-last-capture** mode, walk newest-first and stop at the first
non-pinned tweet whose id is at or below the previous capture's newest,
as the Instagram mode does; tweet ids are time-ordered snowflakes, so an
id comparison is a date comparison.

## One post and its thread

A post page makes `TweetDetail` with `focalTweetId`. The response holds
the focal tweet, the tweets above it in its conversation, and reply
modules named `conversationthread-`; more replies come through cursors of
type `ShowMore` and `ShowMoreThreads`, which the page sends when "Show
more replies" is clicked or scrolled to. *(unverified)* Thread structure
is in the tweets themselves: `conversation_id_str` names the root and
`in_reply_to_status_id_str` the parent, so replies and their depth can be
normalised exactly as Instagram's comments are, with the same per-post
grade (reported count reached, partial, capped, stopped). *(verified)*

Quote posts arrive embedded under `quoted_status_result` on the quoting
tweet; keep the quoted tweet as its own record with a `quoted_by` link,
since a quote of the account by someone else is not the account's post.
Deleted or withheld tweets in a thread appear as `TweetTombstone`
entries; record them as gaps with their reason text.

## Media at full size

### Images

The page loads thumbnails and sized renditions from `pbs.twimg.com`. The
original is a separate request: take `media_url_https` and ask for
`?format=<original extension>&name=orig`. A bare URL returns the
`medium` rendition capped at 1200 pixels; `orig` returns the upload up
to 4096 pixels, and only when `format` matches the upload's own format,
otherwise the server returns nothing. *(unverified; four sources agree)*
This is a real difference from Instagram, where the highest resolution
the page served was the best available: on X, SWM can fetch the original
explicitly, so the manifest can say "original as served for name=orig"
rather than "highest resolution available to the capture". Fetch it
through the existing page-fetch tiers (the CDN is cross-origin, so
`credentials: 'omit'`), and fall back to `name=4096x4096` then `large`.

### Video

`extended_entities.media[].video_info.variants[]` lists progressive MP4
files with a `bitrate` and one HLS playlist (`.m3u8`) without. Every
reader picks the highest-bitrate MP4 and ignores HLS. *(verified)* Follow
them: X's HLS streams carry video and audio as separate renditions whose
audio bitrate is hidden in the group id, which is why yt-dlp needed a
patch to rank them; an MP4 is one file, verifiable by hash, and replays.
*(unverified)* Animated GIFs are also MP4 variants. Record the variant
chosen and its bitrate in the media index, beside `discovered_by` and
`fetched_via`.

## Search and hashtag pages

Both are `SearchTimeline` with `rawQuery` (a hashtag is the query
`#tag`) and a `product` of Top, Latest or Media; the entries have the
same shape as a profile timeline and include the same injected modules.
*(unverified)* Two cautions. First, X ranks and personalises Top results,
and Latest is what the account was shown at that moment, so the manifest
must describe the capture as "what X served this account for this query
at this time", the same wording the Instagram mode refuses to soften for
explore pages. Second, SearchTimeline is one of the operations reported
to validate `x-client-transaction-id` server-side, which does not affect
SWM (the page generates it) but rules out replaying a search by
re-issuing requests. *(unverified)* Attribution has no target here: every
result is a record with its author, and the query and product are the
provenance.

## Sign-in, signed-out visitors, and limits

- **Signed-in is required.** Browsertrix's X behaviour refuses to run when
  the page shows a "Log in" prompt, and the Media tab cannot be visited
  signed out at all. *(unverified)* Plan for the dedicated-account profile
  from the start, as with Instagram.
- **Sign in by hand, once.** Automating the login form triggers
  "suspicious" rejections and CAPTCHAs; a reused browser session with
  `auth_token` and `ct0` is what every reader recommends. *(unverified)*
  SWM's Instagram flow (a window, the curator signs in, SWM reads the
  session) is exactly this.
- **Rate limits are visible.** Responses carry `x-rate-limit-limit`,
  `x-rate-limit-remaining` and `x-rate-limit-reset`. *(verified)* When the
  page hits a limit it shows "Something went wrong. Try reloading." and
  the API answers 429 or JSON error 88; error 32 or 326 means the account
  is refused; error 336 means a client's `features` are stale, which
  cannot happen to a real browser. *(unverified)* Read the reset header
  from the observed 429 and hold the run until then, the way the Instagram
  mode counts rate-limit waits, rather than retrying blind.
- **Domains.** The client lives on `x.com` now: 726 x.com URLs and no
  twitter.com ones in the current operation list. A visit that starts at
  twitter.com is redirected through a migration form; start at x.com and
  it never happens. *(verified)* Media stay on `pbs.twimg.com` and
  `video.twimg.com`.

## Replay

ReplayWeb.page's built-in rules already know X: a GraphQL request under
`x.com/i/api/graphql/` or `twitter.com/i/api/graphql/` is matched on its
path and the `cursor` parameter with fuzzy comparison of the rest, and a
post URL's query string is stripped so shared links resolve.
*(unverified; read from the source file)* Because the calls are GETs
whose operation name is in the path, the collision problem that
Instagram's identical POST URLs could raise does not arise. Two things to
do on SWM's side:

- Capture the MP4 video variant, not the HLS segments, so the archived
  page can play it.
- Apply the lessons of the Instagram replay work to the X writer from day
  one: never rewrite JavaScript, and restate `data-content-len` if X's
  bootstrap uses sized blocks (it is Meta's convention; confirm on the
  first page). Redact the bearer, the CSRF header and cookies on the
  request side, and the session's own ids in bootstrap data.

pywb, which SWM does not use, has an open issue about these long GraphQL
URLs not being found; it is not a wabac problem. *(unverified)*

## What breaks most often, and what SWM is immune to

| Failure | Who it hits | SWM |
| --- | --- | --- |
| Operation ids rotate (documentation regenerated daily; one account of every two to four weeks) | Anyone who builds requests | Immune: read from the page's own URLs |
| `features` flags drift; error 336 when stale | Anyone who builds requests | Immune |
| `x-client-transaction-id` generation changes with the client bundle | Anyone who builds requests | Immune; also the reason not to lend the session to an outside tool for listing |
| Response shapes change (new wrapper types, field moves) | Everyone | Same exposure as Instagram; the provenance layer keeps raw responses so records can be re-derived |
| Account challenges and suspension | Everyone signed in | Same as Instagram: BLOCKED state, a window for the curator |
| Page structure changes that stop a scroll or a tab click from landing | DOM-driving tools | The exposure SWM does carry: its scrolling and tab navigation |
| Sensitive-content interstitials hide media until a "view" click | DOM-driving tools | Needs the click Browsertrix makes, or the media stays unloaded |
| HLS video with split audio | Video fetchers | Avoided by taking the MP4 variant |

## Mapping onto SWM

The Instagram mode is the template; most of it transfers as structure
with new recognisers. In order:

1. **Request describer.** Recognise `/i/api/graphql/<id>/<Name>` from the
   URL path; listing operations are UserTweets, UserTweetsAndReplies,
   UserMedia; the user is `variables.userId`. Simpler than Instagram's
   form-body parsing.
2. **Extractor.** Walk instructions, unwrap tweet results by
   `__typename`, record entryId prefix and instruction type in each
   record's provenance beside response, document and path.
3. **Listing and attribution.** Reuse the scrolling listing with the
   numeric-id rule; skip entries by prefix; treat pinned entries as
   Instagram's pinned posts.
4. **Threads as comments.** Open each selected post's page, read
   TweetDetail, scroll for ShowMore cursors, grade completeness per post
   with the existing statuses.
5. **Media.** Same fetch tiers; add the `name=orig` request for images and
   the highest-bitrate MP4 rule for video; extend the media index with the
   variant chosen.
6. **Redaction and WARC.** Add X's header and cookie names to the
   request-side lists; confirm whether X's HTML uses sized bootstrap
   blocks; keep bundles untouched.
7. **Dashboard and manifest.** An X tab beside Instagram with targets
   (handle, profile URL, post URL, search), the same modes and surfaces
   (Posts, Replies, Media), the same metadata section; manifest wording
   for search and for original-size media.
8. **Fixture and tests.** A fake X server like the Instagram one, serving
   instruction-shaped timelines with injected modules, a pinned entry, a
   thread module, tombstones, and a media host with `name=orig`.

> **Before writing code, confirm three unverified points against a first
> manual capture:** the exact response path for TweetDetail, how a
> promoted item marks itself in the JSON, and whether X's page uses
> `data-content-len` blocks. One profile visit with the response hook on
> answers all three.
